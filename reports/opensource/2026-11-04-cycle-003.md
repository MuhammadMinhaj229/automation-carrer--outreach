## 1. Executive summary

This cycle confirms that ACIOS already has a useful local-first foundation: Python CLI + FastMCP, SQLite persistence, a source/claim provenance workflow, a newer discovery scanner, bounded native HTTP extraction, suppression controls and content-hash-bound human approval.

The highest-value work is not adding another framework. It is resolving correctness and policy gaps between the newer provenance-first path and older discovery/crawling/job modules.

The main findings are:

1. **Legacy event generation can create synthetic business signals labelled as primary-verified.** The legacy Prefect flow contains hard-coded organization/event narratives, uses an ROR website as an event source or a synthetic URL, assigns today's date and a fixed score, then sets `Verified Primary`.
2. **The GDELT path overstates evidence and identity.** It derives an organization from a publisher domain, uses GDELT's seen date as publication date, defaults a global query to Oman, marks aggregator results as primary evidence and can fall back to synthetic records.
3. **Crawler automatic selection contradicts the local-first policy.** The default chain puts the built-in HTTPX adapter last and includes Firecrawl as an automatic candidate. If configured and earlier providers fail, the remote provider may be attempted without a separate per-request opt-in.
4. **The newer GrowthSignalScanner is materially safer.** It explicitly keeps RSS results as discovery leads, preserves unresolved organizations, does not invent event dates/domains and labels the score as a heuristic rather than a probability.
5. **The provenance ledger conflates discovery identity with source-content identity.** `record_discovery_event` can place a discovery-record fingerprint into the source document's `content_hash`.
6. **The existing durable job queue needs a more explicit retry lifecycle.** The inspected SQLite `fail_job` path immediately returns retryable jobs to `QUEUED`; there is no delay scheduling in that method.
7. **GLEIF is the strongest new identity-data candidate.** ACIOS should consider a small HTTPX-based GLEIF adapter for legal-entity enrichment, not another database or mandatory client package.

**Integration decision:** no production code or dependency is changed in this cycle. The P0 evidence and crawler-policy corrections should be implemented and tested before adding a new identity provider. GLEIF is a follow-on integration candidate.

## 4. Code-level findings

### 4.1 P0 — legacy Prefect flow manufactures primary-verified signals

**Files:** `acios/flows/daily_signal_scan.py`, legacy `SignalItem` contract, RSS provider, legacy signals persistence, and `tests/test_prefect_flows.py`.

The inspected `fetch_expansion_signals` implementation contains hard-coded topics and organization/event narratives. It then performs an ROR lookup and sets the source URL to the first matched ROR website, or to a synthetic `https://verified-news.gcc` URL if no result is returned.

For those records it sets:

- `signal_date` to the current UTC date;
- `score` to a fixed 85;
- `evidence_tier` to `Verified Primary`;
- details text that describes the event as verified.

An ROR organization record can help identify a research organization; it cannot prove a plant, investment, contract, pilot or expansion event. A homepage is not the source for a specific event unless the event is actually documented there.

**Risk:** fabricated or unsubstantiated legacy records can look more trustworthy than newer RSS discovery leads.

**Required correction:**

1. Remove the hard-coded sample event creation path.
2. Remove synthetic evidence URLs.
3. Represent missing dates as unknown rather than today's date.
4. Make legacy signal defaults explicitly unverified.
5. Route discovered records through the source/event provenance path.
6. Keep human source classification and claim review as the only way to promote claims to primary-verified status.
7. Add negative tests proving an empty/error provider cannot create a business event.

### 4.2 P0 — GDELT results are overstated as company identity and primary evidence

**File:** `acios/tools/discovery/deep_signal_radar.py`, `scan_gdelt_news_graph`.

The code currently:

- constructs a `sourcecountry` query by taking the first two characters of the country string;
- defaults a global/no-country target to Oman;
- derives `organization_name` from the GDELT article's publisher domain;
- uses `seendate` as `published_date`, with today's date as fallback;
- labels the result `Verified Primary News`;
- generates a generic website from the publisher domain;
- suppresses exceptions and, when no GDELT result remains, falls back to stored local signals, generating a company domain, generic headline and current date where fields are missing.

A publisher domain is not necessarily the company discussed in the article. A GDELT seen/index time is not necessarily the article publication time and is not the business event date. Aggregator discovery does not establish primary verification.

**Required correction:**

- keep GDELT as an aggregator discovery source only;
- preserve GDELT seen/index time separately;
- parse article publication date only when the publisher provides it;
- leave event date unknown until the event itself is evidenced;
- resolve article subject organizations from the article content and independent identity evidence, not publisher domain;
- map country values explicitly using documented country identifiers;
- replace exception swallowing with a typed provider failure state;
- remove fabricated local fallbacks; provider failure or zero results must not create a new event.

### 4.3 Positive finding — newer GrowthSignalScanner uses safer evidence semantics

**File:** `acios/tools/discovery/growth_scanner.py`; tests in `tests/test_discovery_provenance.py`.

The source explicitly documents that RSS results are discovery leads. The tests demonstrate several correct behaviors:

- a generic headline does not automatically become an organization;
- unresolved organizations remain unresolved;
- a news aggregator URL does not become an official company website;
- missing event date remains null;
- publication-date raw text is retained separately;
- source type remains `NEWS_AGGREGATOR_RESULT`;
- status remains `DISCOVERED_NEEDS_PRIMARY_VERIFICATION`;
- the score is explicitly `HEURISTIC_KEYWORD_RELEVANCE_NOT_PROBABILITY`;
- historical database records are not silently repackaged as fresh signals.

**Recommendation:** use this provenance-first path as the reference behavior. Do not weaken it to accommodate old DTOs or legacy flows.

**Remaining gap:** the scanner calls `feedparser.parse` with a feed URL. This uses feedparser's network path rather than fetching bytes through the ACIOS shared HTTPX policy. The current scanner therefore lacks a common ACIOS-level response-byte budget, host rate budget and provider failure telemetry around the feed retrieval.

### 4.4 P1 — automatic crawler order is not local-first

**Files:** `acios/crawling/catalog.py` and `acios/crawling/engine.py`.

The inspected default `automatic_candidates()` order is:

```python
["crawl4ai", "crawlee", "scrapling", "scrapy", "firecrawl", "httpx"]
```

When the environment preference is set, Firecrawl moves to the first position. In auto mode the engine checks which providers are available and tries candidates in order. Consequently, the built-in HTTPX implementation is the last automatic fallback, and a configured Firecrawl integration may be reached automatically after earlier adapters fail.

**Risk:** default behavior does not match the documented preference for ordinary bounded HTTP first; remote paid extraction is part of the automatic fallback chain rather than a distinct per-task opt-in.

**Recommended policy:**

1. Native HTTPX first for ordinary public HTML.
2. Feed the fetched bytes to local extraction.
3. Use browser rendering only when JavaScript is necessary.
4. Require an explicit strategy/consent for remote Firecrawl calls, with a visible usage budget.
5. Keep all provider adapters bounded and independently disableable.

### 4.5 Positive finding — native HTTPX path has useful bounded protections

The native HTTPX path uses a 15-second client timeout, streams response chunks, restricts content to HTML/XHTML, limits response bytes to 2,000,000, follows redirects manually with a maximum of three redirects, validates each redirect URL, and rechecks robots policy after redirects.

These controls should be retained and made the default path.

**Remaining security review items:**

- `_check_robots` obtains `robots.txt` through `client.get` and has a timeout but no visible response-body size cap.
- The DNS check resolves the host before the HTTP request, but the inspected code does not pin the resolved public IP to the actual connection. A DNS rebinding/TOCTOU risk should be addressed or explicitly mitigated.
- Optional browser/crawler adapters may follow redirects internally. The production egress-guard setting is an environment self-attestation; it must not be treated as proof of network-level enforcement.

These are source-level risks to validate with regression/security tests; no exploit test was executed in this research cycle.

### 4.6 P1 — provenance hash fields have mixed meanings

**File:** `acios/core/repository.py`, `record_discovery_event`.

The method derives or accepts a `discovery_record_sha256` fingerprint based on source URL, headline and evidence excerpt. It then passes this value to `record_source_document` as `content_hash`, and uses the excerpt as `content_text`.

A fingerprint of a discovery record is not the SHA-256 of the complete fetched source document. The current field naming can therefore imply content integrity that has not been established.

**Recommended additive model:**

- `discovery_fingerprint`: stable identity for the normalized discovery observation;
- `body_sha256`: digest of the actual fetched response/document bytes;
- `excerpt_sha256`: optional digest of the captured excerpt;
- `canonical_url`: normalized source URL;
- `retrieved_at`, `published_at`, `event_date`: distinct time semantics.

Migration must be additive. Existing records should not be silently reinterpreted as full-body hashes. Existing approval snapshots must be invalidated if hash semantics affecting approved content change.

### 4.7 P1 — SQLite job retry path immediately requeues

**Files:** `acios/core/repository.py` (`fail_job`) and `acios/core/job_queue.py`.

The inspected repository `fail_job` implementation reads attempts/max_attempts and sets the next state to `FAILED` when attempts are exhausted, otherwise it immediately sets the state to `QUEUED`.

No `next_retry_at` schedule or backoff delay is applied in this method.

**Recommended lifecycle:**

- distinguish transient and permanent errors;
- add a bounded `next_retry_at` with exponential backoff and jitter;
- claim jobs atomically and verify the updated row count;
- add a time-bounded worker lease and recovery for abandoned RUNNING jobs;
- preserve idempotency keys across retry attempts;
- make retry count and last failure category inspectable;
- never automatically retry uncertain outbound email acceptance.

This should remain a small SQLite-native workflow. Do not add Celery, RabbitMQ or Redis as mandatory infrastructure.

### 7.1 Recommended signal model

Keep event evidence, organization identity, novelty and opportunity fit separate:

- Evidence tier: official primary / independent secondary / aggregator / unknown.
- Event class: funding, plant/facility, contract, tender, pilot, partnership, sustainability, transformation.
- Identity confidence: stable identifier, official domain, aliases, jurisdiction and unresolved match.
- Time semantics: event date, publication date, retrieval timestamp and unknown.
- Novelty: new event, update, duplicate coverage or repeated source.
- Opportunity fit: sector, geography, workflow pain and skill alignment.
- Hiring intent: separate ATS observation linked to an organization; never proof of expansion.

Do not call any heuristic a probability of a reply, referral, interview or hire without labelled outcome data and calibration.

### 7.2 Recommended GLEIF integration boundary

Use the existing HTTPX transport and repository layer. Store the LEI, legal name, jurisdiction, status, parent relationship, source URL and retrieval time as sourced identity observations. Cache responses conservatively, cap page size and result count, use bounded retries and represent lookup failure explicitly.

Never auto-merge solely on a fuzzy name. Never mark a business event verified because an LEI lookup succeeded.
